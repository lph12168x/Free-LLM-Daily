🆕 今日头条 · 科大讯飞 9/1 开源星火 X2.5-4B / 1.7B：端侧模型原生 1M 上下文，9/7 再发 293B 基座

科大讯飞开源星火 X2.5 端侧模型：4B 与 1.7B 双发，原生 1M 上下文

科大讯飞 · 星火 X2.5-4B / X2.5-1.7B · 原生最长 1M token 上下文 · 强化智能体 / 数学 / 通用理解 · 面向车载 / 智能硬件 / IoT

① 发生了什么：8 月 31 日，科大讯飞向媒体确认将于 9 月 1 日（今天）开源 星火 X2.5-4B 与 星火 X2.5-1.7B 两款端侧通用大模型。 两款模型原生支持最长 1M token 上下文窗口，并重点提升智能体、数学和通用理解三项核心能力， 面向车载、智能硬件、万物互联等端侧场景提供模型支持。 随后在 9 月 7 日，讯飞还将正式发布 星火 X2.5（293B） 基座模型，进一步升级代码与智能体能力。

② 为什么值得关注：把「1M 上下文」和「1.7B/4B 端侧」放在一起，是这一波开源里比较少见的组合。 过去 1M 上下文基本是 30B 以上云端模型的专利，端侧模型普遍停在 32K–128K； 而 4B 级模型量化后大约 2–3GB、1.7B 约 1GB，手机、车机、树莓派级别的开发板都能承载。 对开发者的直接意义是：可以在完全离线、零 API 成本、数据不出端的前提下， 让端侧设备处理整份长文档或整个小代码库——这在车载语音助手、工业巡检、 隐私敏感场景里是刚需，而这些场景恰恰是云端 API 覆盖不到的。

③ 怎么用：开源权重预计同步到 Hugging Face 与魔搭 ModelScope， 本地可用 ollama / llama.cpp / vLLM 直接拉起。 建议先跑 1.7B 验证长上下文检索（RAG 场景填 1M 是不现实的，注意 KV cache 内存开销—— 1M 上下文的 KV cache 在端侧依然是主要瓶颈，实际建议控制在 128K–256K 区间）。

④ 与现有免费栈怎么配合：端侧模型不适合扛重推理，推荐做成两级路由—— 端侧 X2.5-1.7B 负责离线兜底、意图识别、隐私数据预处理； 需要重推理时再上行到云端免费额度（NVIDIA NIM 的 Kimi K3 / DeepSeek V4 Flash，或 OpenRouter 的 :free 池）。 这样既守住隐私和成本，又不牺牲上限。
